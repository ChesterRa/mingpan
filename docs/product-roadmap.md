> 建立日期：2026-08-28
> 定位：中華術數 MCP 生態的**確定性排盤基座**——MCP=計算器，Agent=分析師

## 一、產品分層診斷（2026-08-28 復盤）

| 層 | 現狀 | 判斷 |
|----|------|------|
| 引擎層（計算） | 六術數齊備；奇門四類口徑缺陷已修（雙源驗證）；八字年柱立春換年已修（歷史人物金樣本）；206 測試；跨時區可復現（CI TZ 矩陣） | ✅ 可信 |
| 輸出層（渲染） | 輸出契約已確立：**只輸出確定且權威且 AI 不易獲知的量**。八字=四柱納音/天干藏干十神/十二長生自坐/命宮胎元/旬空/公農曆；紫微=宮位星曜亮度/五行局命主身主/四化；五行強弱、格局吉凶、用神喜忌、神煞、評分、斷語一律不進輸出 | ✅ 契約已固化 |
| 輸入層（schema） | zod 校驗 + 可讀錯誤 + 時區 + 時間起課；listTools 線路載荷 38.8→35.3KB | ✅ 良好 |
| 分發層（增長） | npm 月下載 ~125；未進入任何 MCP 目錄/註冊表 | ⚠️ 最大缺口 |
| 解讀層（Agent 側） | 輸出僅含確定性事實（格局檢測平列、用神落宮旺衰、主客生克）；解讀指南文檔已有 | 維持邊界，不越位 |

**兩條教訓（2026-08-28）**：
1. bazi_basic 輸出殘缺（~100 字）存在了整個產品生命週期而未被發現——測試只覆蓋計算器、
   不覆蓋「用戶實際拿到的文本」。結論：**每個工具必須有輸出契約測試**。
2. 修復殘缺輸出時曾矯枉過正，把服務層算出的五行/用神/格局/神煞全量渲染出去——
   這些恰是無權威口徑的解讀層，屬 AI 職責。結論：**「服務算了什麼」不等於「該輸出什麼」**，
   輸出的準入條件是三個「確定、權威、AI 不易獲知」同時滿足
   （歷屆判例：干支/節氣/納音/藏干/十神/十二長生/命宮胎元=確定查表 ✓ 入選；
     五行力量=帶權重判斷 ✗；格局吉凶/用神喜忌/神煞/評分/斷語=無權威口徑 ✗）。

## 二、用戶旅程與痛點對照

```
用戶提問 → Agent 選工具 → 填參數 → 排盤計算 → 解讀輸出
   │            │            │           │            │
  分發缺口    工具面 35KB   校驗+錯誤   正確性✅     半解讀信息✅
  (待解決)   (已優化)     已解決✅    已解決✅     知識在 Agent 側
```

- **發現**：提交 MCP 官方 servers 目錄與 smithery 等註冊表是零成本高槓桿動作
- **選擇**：16 個工具名語義清晰，維持不動（評估過列表工具合併：省載荷但犧牲 API 清晰度且 breaking，收益不成立）
- **填參**：農曆/公曆/時區三入口統一在入口層歸一化，已完成
- **解讀**：不越位做自動斷卦；`docs/qimen-yongshen-guide.md` 類解讀指南按需補充

## 四、工程紀律（延續既有原則）

1. 口徑變更：先更新文檔再改代碼，雙源交叉驗證（經典文獻 + 開源 oracle）
2. 每個工具：計算器測試 + 輸出契約測試 + （有 oracle 時）金樣本
3. 可復現性：CI 強制 TZ 矩陣（Asia/Shanghai / UTC / America/New_York）
4. 依賴：zod 鎖 v4（SDK 1.30 + zod 3.25 會觸發 TS2589 類型爆炸）
5. stdio 服務器：日志一律走 stderr，stdout 只允許 JSON-RPC
